One run, end to end

An actual run, recorded on 2026-08-30: a markdown-to-static-site generator built by free models across four wallets in 7 minutes 38 seconds, then independently verified. Every number below is from the journal, not an illustration. Two later runs — one wide, one deliberately starved — are compared at the end.

Read this for the mismatches. Two things below are probably not what you are picturing: no .md files are written for the workers, and the coordinator does not assign agents to tasks. Each is called out where it happens.

This page used to be a composite. It is now a real run — 6 tasks, 0 failures, 419 lines of working Python. The failure catalogue in section 05 remains drawn from the test suite, because no real run has yet hit a provider failure mid-build — see section 07.

01b

What discovery refuses to schedule

new

Before quality is even a question, a model has to be able to do the job. Ten of the 77 free models on this machine cannot, and every one of them was previously drawable.

ExcludedContextWhy it would have failedCaught by
google/lyria-3-pro-preview1,048,576 generates music — output modality ["text","audio"] non_text_output
google/lyria-3-clip-preview1,048,576 same familynon_text_output
nemotron-3.5-content-safety128,000 a classifier — it scores text, it does not write it not_a_generalist
liquid/lfm-2.5-2.6b65,536 2.6B parameters and too little context for a real task context_too_small
minimax/minimax-m2.7196,608 capable, but under the 200K floor — arguably collateral context_too_small

Why a context floor alone is not enough

The two music models carry a 1,048,576-token context — larger than anything else on the machine. Every context floor in the world would have waved them through. Only the declared output modality gives them away, and the models --verbose listings do not publish it, so the family name is matched as a fallback.

What it saves

Nothing is deleted and no network call is made — the reason is recorded and shown per lane. The saving is in requests: each of these was drawable at score zero, and every draw spends a full lane request that was never going to succeed. That is the resource that is actually scarce.

Metadata is pooled per model across lanes, because context belongs to the model, not to whichever wallet happens to list it.

02

Coordinator — and the first mismatch

You start any agent and paste one file. There is no second prompt, no mode selection, and no roster to activate.

opencode                      # or kilo / hermes / cursor / copilot
> paste .free-agents/prompts/coordinator.md
> a markdown-to-static-site generator: parser, template engine, cli, tests

What the coordinator does next

  • Recognises this as a build that may split — the only route that uses lanes
  • Runs fa lanes → 5
  • Names 6 tasks and checks their file sets are disjoint
  • Writes the sample content file itself — dispatching that would cost more than doing it
  • Both gate conditions hold → orchestrate

Mismatch 1 — no .md files are written

The only .md in the flow is coordinator.md, which ships with the tool. The plan is a single JSON file, .orch/tasks.json. No per-task briefs, no role documents, no roster file. If you pictured a folder of generated markdown, that does not exist.

Mismatch 2 — the coordinator does not pick agents

Nothing in a task names an agent or a model. The coordinator says what; the engine decides where, per attempt, by ranking wallets and models. A task can start on hermes and finish on kilo. If you pictured assigning "researcher → agent A", that layer does not exist — it was deliberately removed, because assignment cannot see live wallet health and ranking can.

What each worker actually receives updated

For a task with no dependencies, two things:

Your working directory is /root/mdsite
Create and edit files only inside it, using
paths relative to it. Do not use absolute paths.

Create parser.py: a minimal Markdown-to-HTML
converter with YAML-ish front matter…

For a task that has dependencies, its dependencies' handoffs are prepended, and — if anything depends on it in turn — a request for one is appended. Still no repo listing, no conversation, no transcript.

03b

Handoffs — and the thing they caught

proven

This is the clearest evidence the feature does what it was built for, and it was not planted. template implemented something the spec never asked for, said so in its handoff, and build matched it.

# what my spec asked for
render(template, context) -> str
    Replaces {{ key }} with str(context['key']).

# what template.py handed back, unprompted
---HANDOFF--- template.py exposes `render(template, context)` and
`render_file(path, context)` with `{{ key }}` (including dotted `{{ user.name }}`)
substitution and `{% for item in items %}...{% endfor %}` block iteration,
missing keys render empty.

# what build.py then wrote, having received that line
42:        for part in key.split("."):
46:            if ctx == "" and part != key.split(".")[-1]:

Why this could not have happened before

Dotted paths are not in the spec and are not visible from build.py's side without reading another file — which a worker cannot do, because it receives a string, not a repository. Before handoffs, build would have implemented flat keys only and quietly lost the capability.

All three handoffs from this run

parser → "parse(text)->(dict,str) and to_html(str)->str; next task can import both directly"

template → the line above

build → "build_site(content_dir, out_dir, template_path=None) and DEFAULT_TEMPLATE; it scans .md files…" — which is what cli then imported.

Mismatch 3 — "token limited" is not a state

There is still no token budget. Prompt size is now measured and reported (est_prompt_tokens), but nothing counts spend against a quota. On free models the scarce resource is requests per credential, not tokens, so nothing counts or budgets them. What you would call "token limited" arrives as one of two things: a provider saying rate_limited / no_credits (a wallet fault, which cools the wallet), or context_overflow — which blames nobody and asks the caller to send less. If you want a token budget, it is a feature to add, not one to find.

Do not over-read this

The previous run went 1 of 4, then 4 of 4 after the specs named the exact failure modes. This one was 6 of 6 first time. Most of that difference is spec quality — precise interface contracts, written because the earlier run taught me to — and some is the filtering, which removed 10 models that could otherwise have been drawn.

It is not evidence that free models got better.

07

Two more runs, and what they changed

mdsite was chain-shaped, so it never stressed the scheduler. Two follow-ups did — and the starved one corrected something stated earlier on this page.

RunShapeTasksPeak lanesRequeuesLimiting factor
mdsitechain630the dependency graph
fmtkitwide854the lane count
coldrunstarved519one wallet, deliberately

Correction — the gate is about speed, not safety

coldrun orchestrated on one lane, which the gate explicitly forbids, to see how it would fail. It did not fail: 5 of 5 tasks completed, all five modules correct. It simply serialized them.

So lanes >= 2 is advice about throughput, not correctness. The rule stands — orchestrating on one lane buys nothing — but "do not orchestrate below two lanes" reads like a warning about breakage, and it is not one.

Confirmed by starvation

  • 9 requeues, 0 attempt failures. A task that cannot get a lane is not a task that failed — no retry budget was consumed.
  • The journal survived repeated requeueing intact. That matters more than the code: it is the only thing resume can read.
  • resume correctly re-ran nothing.

What three runs still have not shown

Across mdsite, fmtkit and coldrun — 19 tasks, not one real provider failure mid-build. Every incident in section 05 remains verified by the test suite and by nothing else. coldrun was built specifically to force one and could not: this free tier is more generous than expected.

That gap should close by itself on a genuinely large build. Forcing it by hammering providers would be the wrong way to get the evidence.

Δ

If your mental model differs, this is where

  • No generated markdown. One shipped prompt in, one tasks.json out. Workers get a string, not a document.
  • No roster and no assignment. Tasks never name an agent. The engine chooses per attempt from live wallet health — which is why a rate limit reroutes instead of stalling.
  • Cold ordering is metadata, not a leaderboard. A fresh registry knows nothing — 0 of 418 models had stats — so unproven models are ordered by context, output budget and a name hint, plus an optional offline seed file you edit. Nothing is fetched at runtime, and one real success outranks any prior.
  • Prompt size is measured; spend is not. You get a warning when a spec is oversized, but there is no token budget and no per-lane ledger. Requests per credential remain the scarce thing.
  • Handoffs now exist, in the cheap form only. build received one line each from parser and template — their own claims, not generated summaries. There is still no shared scratchpad and no transcript passing.
  • Parallelism is 5 here, not 3. Two agents each serve two wallets. Lanes are credentials, so the count follows keys, not CLIs.
  • The coordinator is one of the workers' peers, not a supervisor. It does the small tasks itself and dispatches only the substantial ones.

Sections 00–06 are one real run on this machine, recorded 2026-08-30: timings, wallets, model names and handoff text come from .orch/journal.ndjson and the generated files. Section 05 is the exception and says so — this run hit no failures, so that catalogue is drawn from earlier runs and from the 185-assertion test suite.
